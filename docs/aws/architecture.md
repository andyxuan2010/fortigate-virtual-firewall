# AWS FortiGate implementation

The AWS composition in `platforms/aws` mirrors the Azure root's two deployment modes:

| Mode | Nodes | Interfaces per node | Availability zones |
| --- | ---: | --- | --- |
| `single` | 1 | external, internal | first configured AZ |
| `ha` | 2 | external, HA, internal, management | first and second configured AZs |

The VPC, subnet, security-group, IAM-role, FortiGate, and Gateway Load Balancer foundations use the public modules from [aws-template](https://github.com/andyxuan2010/aws-template):

- `modules/vpc`
- `modules/security_group`
- `modules/iam_role`
- `modules/fortigate`
- `modules/gateway_load_balancer`

The `fortigate` module owns the FortiGate EC2 instances, multi-ENI topology, static private IPs, source/destination checks, FortiOS bootstrap MIME content, and active-passive HA configuration. The `gateway_load_balancer` module owns the GWLB, GENEVE target group, listener, health check, and FortiGate traffic-interface target registrations.

Simple mode creates one external and one internal subnet/ENI. HA mode creates external, HA, internal, and management subnets/ENIs for nodes `a` and `b`, with the two nodes placed in separate AZs. The HA heartbeat and hostname bootstrap is generated by the FortiGate module; additional FortiOS CLI configuration and any BYOL license file are supplied through root inputs.

HA production enables the Gateway Load Balancer example. GWLB endpoints, endpoint services, route-table steering, and the final FortiOS GENEVE configuration remain caller responsibilities. The optional static workload route resource is still manual because the route-manager module is not yet available from the public `main` branch.
